# LLM 编码行为准则

> 此文件扩展 [coding-style.md](coding-style.md)，补充防止 LLM 常见编码错误的行为纪律。
> 源于 [Andrej Karpathy 对 LLM 编码缺陷的观察](https://x.com/karpathy/status/2015883857489522876)。
> **QSS 定位**: 技术科学层 — 约束编码行为的理论原则，指导工程技术层的具体实践。
> 详细反面教材见 skill: `/karpathy-guidelines`

## 权衡

这些准则偏向**谨慎优先于速度**。对于琐碎任务（拼写修正、明显的单行改动），自行判断——并非每次改动都需要完全严格的流程。

---

## 1. 先想再写

**不要假设。不要隐藏困惑。主动呈现权衡。**

实现之前：
- 明确陈述你的假设。如果不确定，**提问**——不要猜。
- 如果存在多种解释，**全部呈现**——不要默默选一个。
- 如果存在更简单的方法，**说出来**。在合适的时候提出反对意见。
- 如果有不清楚的地方，**停下来**。明确指出困惑之处。提问。

> **QSS 对齐**: 对应"从定性到定量综合集成法"——在做（定量）之前，先把理解（定性）做扎实。不假设 = 不跳过定性阶段。

## 2. 简单优先

**用最少代码解决问题。不要做推测性开发。**

- 不添加需求之外的功能。
- 不为单次使用的代码写抽象。
- 不添加未要求的"灵活性"或"可配置性"。
- 不为不可能发生的场景写错误处理。
- 如果你写了 200 行代码但其实 50 行就够了，重写它。

问自己：*"高级工程师会说这过于复杂了吗？"* 如果是，简化它。

> **与 coding-style.md 的关系**: coding-style.md 的 KISS/YAGNI 是原则陈述，本条是其**行为执行层面**的具体化。

## 3. 精准变更（关键）

**只碰你必须改的。只清理你自己造成的混乱。**

> ECC 体系中此前缺失的维度。这是四条原则中对 diff 质量影响最大的一条。

编辑已有代码时：
- ❌ 不要"改进"相邻的代码、注释或格式。
- ❌ 不要重构没有坏的东西。
- ✅ 匹配已有风格，即使你更倾向于别的写法。
- ✅ 如果你注意到无关的死代码，**提出来**——不要直接删除。

当你的改动造成孤立代码时：
- ✅ 删除因你的改动而变得无用的 imports/变量/函数。
- ❌ 不要删除已有的死代码，除非被要求。

**检验标准**：每一行改动都应该能直接追溯到用户的请求。

> **QSS 对齐**: 对应"边界清晰"原则——系统组件的边界就是"用户请求的范围"。越界修改破坏了系统层次间的契约。

## 4. 目标驱动执行

**定义成功标准。循环直到验证通过。**

将命令式任务转化为可验证的目标：

| 而不是... | 转化为... |
|-----------|----------|
| "添加验证" | "为无效输入编写测试，然后让它们通过" |
| "修 bug" | "编写能复现 bug 的测试，然后让它通过" |
| "重构 X" | "确保测试在重构前后都能通过" |

对于多步骤任务，陈述简要计划：
```
1. [步骤] → 验证: [检查]
2. [步骤] → 验证: [检查]
3. [步骤] → 验证: [检查]
```

强有力的成功标准让 Agent 能独立循环。弱标准（"把它做好"）需要不断的澄清。

> **与 testing.md/development-workflow.md 的关系**: testing.md 提供了 TDD 方法论，本条是其**任务级执行**——把任何模糊需求转化为 TDD 可验证的目标。

## 反面模式速查

| 原则 | 反面模式 | 纠正 |
|------|---------|------|
| 先想再写 | 默默假设文件格式、字段、范围 | 列出所有假设，请求澄清 |
| 简单优先 | 为单个折扣计算写策略模式 | 一个函数，等复杂度真正需要时再重构 |
| 精准变更 | 修 bug 时顺便改引号风格、加类型注解 | 只改动修 bug 所需的行 |
| 目标驱动 | "我来看看代码然后改进一下" | "写出复现 bug X 的测试 → 让它通过 → 验证无回归" |

---

## 如何判断准则生效

以下信号说明准则在起作用：

- **diff 中的不必要改动减少** — 只有被请求的改动出现
- **因过度复杂而重写的次数减少** — 代码一次就够简单
- **澄清性问题在实现之前提出** — 而非在犯错之后
- **PR 干净简洁** — 没有顺路重构或"改进"
