# QSS 门禁模板

**Extracted:** 2026-06-30
**Context:** claude-md-layer-gate 是目前唯一成功落地的 QSS 门禁。分析其结构后发现它遵循一个可复用的 7 元素模式。本模板将这个模式抽象出来，用于未来创建新门禁时直接套用。

## 门禁的 7 个必备元素

| # | 元素 | 说明 | claude-md-layer-gate 中的对应 |
|---|------|------|---------------------------|
| 1 | **触发条件** | 机械可检测的、高频的、无歧义的动作 | "修改 CLAUDE.md 添加规则" |
| 2 | **二元分支流程图** | 每个判断点只有是/否两个出口，不允许"看情况" | 层次审核流程图（含工具名？是→阻止 / 否→继续） |
| 3 | **层次映射表** | 显式的"允许/禁止"列，把抽象原则翻译为具体信号 | 五层→文件+允许内容+不允许内容 |
| 4 | **负面示例** | 具体文本模式 + 为什么错 + 正确写法，至少 1 组对比 | ❌ CLAUDE.md 塞命令 vs ✅ CLAUDE.md 只指路 |
| 5 | **grep-able 决策信号** | 具体的工具名、CLI 命令、禁用词——可被机械匹配 | "WeasyPrint"、"禁止"、"永远不要" |
| 6 | **自包含** | 不要求阅读 QSS 参考文献就能执行门禁，所有判断逻辑内嵌 | 整个门禁在一个文件内自解释 |
| 7 | **存储为 learned rule** | `user-invocable: false`, `origin: auto-extracted`，索引在 learned/SKILL.md | 头部 YAML + learned 索引行 |

## 为什么 claude-md-layer-gate 成功了

它没有说"先读 QSS 参考文献，理解五层大厦"，然后让你自己做判断。它直接给了你一个**可操作的流程图**和**机械化的决策信号**：

```
要写入 CLAUDE.md 的规则
  ↓
问：这条规则包含具体工具名/CLI 命令/错误消息吗？
  ├── 是 → 不应该放 CLAUDE.md → 放入 learned skill，CLAUDE.md 只写一句指路
  └── 否 → 问：这是"项目是什么/去哪找"还是"怎么做"？
           ├── 是什么/去哪找 → ✅ 可以放 CLAUDE.md
           └── 怎么做 → ❌ 应该放 learned skill 或 SKILL.md
```

**关键洞察**：门禁的成功不取决于哲学深度，而取决于**操作确定性**。回答"这条规则包含 `python -m` 吗？"比回答"这条规则在五层大厦的哪一层？"容易 100 倍。

## 门禁设计流程（填空式）

### Step 1：选择触发动作
此门禁绑定到哪个具体的、机械可检测的动作？

- [ ] 动作名称：__________________
- [ ] 触发频率：每次 / 每天 / 每周
- [ ] 机械检测方式：__________________
- [ ] 例外情况（什么情况下不触发）：__________________

**设计要求**：动作必须足够具体。❌ "做重大决策时" — 太模糊。✅ "往 CLAUDE.md 写新规则时" — 机械可检测。

### Step 2：设计二元分支
每个判断点的答案只能是"是"或"否"。不允许"看情况"或"部分符合"。

```
触发动作发生
  ↓
问：__________________？
  ├── 是 → __________________
  └── 否 → 问：__________________？
                ├── 是 → ✅ __________________
                └── 否 → ❌ __________________
```

**设计要求**：
- 最多 2-3 层分支。超过 3 层说明门禁太复杂，需要拆分。
- 每个问题必须是**事实判断**（"是否包含 X"），不是**价值判断**（"是否足够好"）。
- 终止节点必须是 ✅ PASS 或 ❌ STOP + 具体行动。

### Step 3：构建映射表

| 层级/类别 | 允许的内容 | 不允许的内容 |
|----------|-----------|------------|
|          |           |            |

**设计要求**：
- "允许"和"不允许"列中的内容必须是**具体示例**，不是抽象原则。
- 每行对应一个明确的决策路由。

### Step 4：编写负面示例
至少两组 ❌/✅ 对比，每组包含：
1. 具体的错误文本
2. 为什么错（违反了哪个原则）
3. 正确的写法是什么
4. 标注 grep-able 决策信号

### Step 5：列出 grep-able 信号

```
| 门禁输出 | grep-able 信号 |
|---------|---------------|
| ❌ 某类失败 | 具体的关键词/命令/模式 |
| ✅ 通过 | 具体的关键词/命令/模式 |
```

### Step 6：写入 learned index

在 `learned/SKILL.md` 中增加一条记录：
```
| N | YYYY-MM-DD | <一句话描述> | [<文件名>.md](<文件名>.md) |
```

## 设计原则总结

> **门禁不是哲学考试——它是路标。**
> 好的门禁让 LLM 在 30 秒内做出正确路由决策。
> 坏的门禁要求 LLM 先理解一个哲学体系再做决策——等于没有门禁。
