# 框架采用率审计方法

**Extracted:** 2026-06-30
**Context:** 对 qian-system-science 在 CLAW 中的实际落地情况进行审计时形成的方法。核心发现：QSS 142 次引用中 ~110 次是自引用，仅 1 处真正落地为门禁。该方法可复用于任何"宣称遵循 X 框架"的项目。

## Problem

项目宣称"遵循某某框架/方法论"，但实际落地程度未知。常见的错觉：
- 框架文档写了 10 万字 → 以为已经落地了
- 顶层 CLAUDE.md 写了一句话 → 以为每次会话都在用
- 引用次数看起来很多 → 但大量是框架引用自己

在没有审计方法之前，框架的落地状态是一个"薛定谔的盒子"——既可能已经发挥作用，也可能完全是纸上谈兵。

## Solution

### 四步审计法

#### Step 1: grep 全量引用扫描

```bash
grep -rn "框架关键词1\|框架关键词2\|核心概念3" \
  --include="*.md" \
  --include="*.ts" \
  --include="*.py" \
  项目目录/ \
  用户配置目录/
```

目的：找到所有提及框架的文件，统计引用次数。

#### Step 2: 引用深度分级

将每个引用文件按深度分为 4 级：

| 等级 | 标记 | 含义 | 示例 |
|------|------|------|------|
| **A — 自引用** | 🔵 | 框架自身的文档引用自己 | `qian-system-science/SKILL.md` 引用 `synthesis-framework.md` |
| **B — 被动上下文** | 🟡 | 在全局配置中作为"背景知识"出现，但无执行机制 | `AGENTS.md` 中的 QSS 决策检查清单 |
| **C — 浅层引用** | 🟠 | 偶发性提及，仅一句话带过，无系统性映射 | `ai-video-factory/SKILL.md` 中的"以人为主" |
| **D — 深度落地** | 🟢 | 作为可触发、可执行的门禁或检查点 | `claude-md-layer-gate.md` |

> ⚠️ **观察者效应**：审计结果公布后，被审计的框架通常会被改进——新门禁被创建、引用文件数增长。下一次审计的基线就变了，这是正常的，不是审计方法失效。审计的价值恰恰在于触发了这种改进。建议在审计报告的末尾注明"本审计报告发布于 YYYY-MM-DD，下次审计时以此为基线对比"。

#### Step 3: 计算真实采用率

```
真实采用率 = D 级文件数 / 项目总组件数
```

- 如果采用率 < 5%：框架处于"纸面存在"阶段
- 如果采用率 5-20%：框架有少数落地，但远未普及
- 如果采用率 > 20%：框架已经实质性地影响项目运作

#### Step 4: 差距分析 + 改进建议

对照框架自身的核心原则，逐项检查：
1. 每个核心原则是否有对应的可执行机制？
2. 原则中哪些已落地？哪些仅存在于文档？
3. 已落地的案例中，成功模式能否复制到未落地的原则？

输出格式：
- 🚨 差距清单（按严重程度排列）
- 💡 改进建议（按优先级排列）
- 📊 一份可供人工查阅的 HTML 审计报告

> ⚠️ **如果是重复审计（非首次）**：必须附上一张对比表——上次审计的 D 级文件数、采用率、差距清单闭合率——以追踪趋势而非单点快照。两次审计之间的变化方向（改善/恶化/持平）比单次数字更有意义。

### 审计报告模板

审计报告 HTML 应包含 7 个板块：
1. 核心数据看板（关键数字一目了然）
2. 框架资产自身质量评估
3. 逐文件引用分布统计表
4. 逐项落地深度评估
5. 差距清单（Gap List）
6. 根因分析
7. 改进建议（按 P0/P1/P2 排列）

## When to Use

- 怀疑某个"宣称遵守的框架"实际上没有落地时
- 新接手一个项目，需要快速评估其方法论的执行状态
- 框架引入 N 个月后，做效果回顾
- 任何需要在"我们认为的"和"实际发生的"之间做事实核查的场景

## 适用范围与局限

本方法适用于以 `.md` 文件为主的文本知识体系（skills、rules、memory、AGENTS.md 等）。如项目引入新的知识存储形式（向量数据库、外部 wiki、非文本配置等），需先确认是否可 grep 扫描——如不可，需要扩展方法或使用专用检索工具。

本方法测量的是"引用 + 落地"，不测量"行为是否真的改变了"。一个门禁存在于文件中 ≠ 它每次都被触发执行。如需验证真实行为改变，需配合会话日志分析或哨兵异常检测。

## 关键教训

> **引用次数 ≠ 采用程度。**
> 一个框架被提到了 100 次，不代表它被用了 100 次——可能 80 次是框架自己引用自己。

> **背景知识 ≠ 执行机制。**
> 规则被加载到 system prompt 里，不等于 LLM 会执行它。规则被动加载陷阱（[[rules-passive-loading-trap]]）会导致框架原则在任务模式下被跳过。

> **框架的真正落地需要"门禁"而非"文档"。**
> 框架原则要从"建议你去读"变成"必须通过"，需要：触发条件 + 二元判断 + 可操作输出。
