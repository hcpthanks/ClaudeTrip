# QSS 技能创建门禁

**Extracted:** 2026-06-30
**Context:** 当前技能创建流程（writing-skills）缺少系统论审核步骤——用户说"建个 skill"→LLM 直接写 SKILL.md→完成。没有层次定位检查，导致技能可能放错层、边界模糊、没有反馈机制。本门禁将 synthesis-framework.md 的"最低三问"转化为三个二元分支判断。

## Problem

每次创建新 skill 的默认路径是直接动手写。但 skill 创建是一个**系统组件添加**——它在钱学森五层大厦中应该有一个明确的层位、与已有组件的清晰边界、以及从产出回到输入的反馈回路。

跳过系统论审核会导致：
1. **层次污染**：工程技术层的"怎么做"被放入基础科学层的 skill
2. **边界模糊**：两个 skill 做重叠的事情，Agent 路由时不知道该选哪个
3. **无反馈回路**：skill 被写入后从未被评估，纸面存在但实际无用

## Solution

**每次要创建或大幅修改 skill 时，必须先通过以下门禁：**

### 门禁流程图

```
创建/修改 skill 的意图
  ↓
Q1：这个 skill 在五层大厦的哪一层？
  ├── 回答模糊/说不清 → ❌ STOP：先把定位想清楚
  └── 回答明确 → 继续
                    ↓
Q2：和已有组件的关键区别是什么？
  ├── 与已有 skill 功能重叠 → ❌ STOP：先明确分界或考虑合并/退役
  └── 边界清晰 / 明确互补 → 继续
                              ↓
Q3：反馈回路是什么？
  ├── 没有反馈机制 → ❌ STOP：先设计反馈回路
  └── 有明确的评估/改进机制 → ✅ PASS：可以开工
```

## Q1：我在五层大厦的哪一层？

### 层次定位表

| 层级 | 在 CLAW 中的对应 | 典型 skill 示例 | 核心特征 |
|------|-----------------|---------------|---------|
| **哲学+桥梁** | 指导思想、设计原则 | `qian-system-science` | 关于"如何组织系统"的元方法 |
| **基础科学：系统学** | 核心方法论、编排方法 | `planning-with-files`, `autoresearch`, `brainstorming` | 以方法论/流程/判断原则为主 |
| **技术科学** | 技术类规范、审查方法 | `code-review`, `security-review`, `systematic-debugging` | 以规范/标准/检查清单为主 |
| **工程技术** | 具体执行、工具使用 | `ai-video-factory`, `hyperframes`, `slideshow` | 以具体工具名/CLI命令/文件路径为主 |

### 决策信号（grep-able）

| 信号 | 指向层次 |
|------|---------|
| 内容大量出现具体工具名/CLI命令/文件路径/API 参数 | **工程技术层** |
| 内容以方法论/流程/判断原则为主线 | **技术科学或基础科学层** |
| 内容是关于"如何组织系统/编排组件/设计架构"的元方法 | **基础科学层** |
| 内容是关于"系统的根本目的/哲学原则/世界观" | **桥梁层** |

### 自检语句模板

> "我这个 skill 属于 **[层名]**，因为它的核心职责是 **[一句话]**，典型内容包含 **[特征]**"

### ❌ 常见错误

| 错误 | 示例 | 为什么错 |
|------|------|---------|
| 工程技术伪装成基础科学 | 把"ffmpeg 常用命令合集"放入基础科学层 | 具体工具命令属于工程技术层 |
| 技术科学伪装成桥梁 | 把"React 状态管理最佳实践"放入桥梁层 | 特定框架模式属于技术科学层 |
| 绕过整个分层 | 说"我这个 skill 横跨多层"作为不分层的借口 | 每个 skill 有主导层次；如有真正跨层需求应显式标注原因 |

## Q2：我和其他组件的关系是什么？

### 必须执行的操作

1. 用 `grep` 搜索已有 skills 中是否有类似功能的关键词
2. 确认新 skill 与最近的同类 skill 至少在一个维度上有明显区别：输入类型 / 输出类型 / 使用场景 / 质量等级 / 抽象层次
3. 如果完全替代已有 skill，必须同时规划旧 skill 的退役或合并

### 关系决策矩阵

| 与已有 skill 的关系 | 行动 |
|-------------------|------|
| 完全覆盖已有 skill | 先退役旧的，再建新的（或直接合并到旧的） |
| 部分重叠但关键维度不同 | 在 description 中明确区分关键词 |
| 与已有 skill 互补 | 在 description 中写明"与 X 互补，用于 Y 场景" |
| 无可替代 | 标注为领域内唯一 skill |

### ❌/✅ 对比

**❌ 错误**：
> "我新建一个 `video-maker` skill。和已有的 `ai-video-factory` 差不多，但我的更简单。"
→ 问题：没说清楚关键区别是什么维度不同。如果只是"更简单"，应该在 ai-video-factory 内部提供简化模式。

**✅ 正确**：
> "我新建一个 `video-batch-processor` skill。它和 `ai-video-factory` 的关键区别是：输入是 CSV 批处理清单（而非单个脚本），输出是 N 个并行视频（而非 1 个），使用场景是批量生产而非创意制作。`ai-video-factory` 覆盖单个视频的精细制作，`video-batch-processor` 覆盖批量的自动化生产。两者互补。"

## Q3：我参与了哪个螺旋上升的过程？

### 反馈回路检查

| 检查项 | 要求 |
|--------|------|
| 谁来评估效果？ | 用户反馈？自动指标？定期审计？——必须有明确答案 |
| 评估结果如何驱动改进？ | 更新 SKILL.md？触发退役评估？追加 learned rule？ |
| 是否设置了回顾日期？ | `review_date: YYYY-MM-DD`（建议 30 天后）写入 SKILL.md frontmatter |

### ❌ 反例（直接拒绝）

- "用户会告诉我好不好用" → **太被动**
- "有问题时会修复" → **没有定期检查机制**
- "这是个一次性的工具" → **所有 skill 都会面对环境变化**

### ✅ 正例（可以接受）

- "每 30 天检查一次触发频率，连续 30 天零触发触发退役评估"
- "SKILL.md 中记录每次重大修改的原因和日期"
- "产出后 7 天内由用户验收，验收结果写入 learned"

## 门禁判定

```
三个问题全部通过 → ✅ PASS：可以进入 writing-skills 的 RED Phase
任一问题不通过 → ❌ STOP：必须先解决该问题
```

## 与 writing-skills 的集成

在 writing-skills 的 Skill Creation Checklist 中，**RED Phase 之前**插入：
```
- [ ] QSS 门禁通过？三个问题全部 PASS 才能进入 RED Phase
```

## 与 AGENTS.md 的关系

AGENTS.md 的 QSS 决策检查清单已包含"边界清晰吗？""层次对吗？""反馈闭合了吗？"三条。本门禁将这三条从**被动上下文**转化为**针对"创建 skill"这一特定动作的主动检查点**。

## 决策信号汇总

| 门禁输出 | grep-able 信号 |
|---------|---------------|
| ❌ Q1 失败 | "不太确定"、"可能是"、"横跨多层"（无具体理由） |
| ❌ Q2 失败 | 已有 2+ 个 skill description 含相同核心功能词 |
| ❌ Q3 失败 | 无 `review_date`、无反馈描述、"用户会告诉我的" |
| ✅ 全部通过 | 三个问题各有明确的一句话回答 |
