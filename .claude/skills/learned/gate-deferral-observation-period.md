# 门禁延期决策 + 观察期数据采集

**Extracted:** 2026-07-01
**Context:** qss-ecc-alignment 门禁的对抗验证发现 4 个缺陷（已修复），同时发现触发条件不够机械可检测，建议拆分为 2 个独立门禁。但拆分需要实际使用数据支撑，不应在零数据情况下提前拆分。

## Problem

设计一个门禁/规则/检查 → 对抗验证发现它需要被拆分/升级 → 但没有实际使用数据来支撑拆分决策。常见陷阱：
- **提前拆分**：在没有数据的情况下设计更细的门禁 = 纸面上猜测，可能拆错方向
- **无限期拖延**：发现缺陷但不设观察期 = 缺陷永远不会被修复
- **过度采集**：为"收集数据"建一个需要管理的大项目 = 数据采集本身变成负担

## Solution: 三阶段模式

### 阶段 1：对抗验证 + 即时修复（立即可做）
- 对抗验证找出所有缺陷
- 能在当前结构内修复的 → 立即修复
- 需要结构变更才能修复的 → 记录到"待改进清单"，不立即执行
- 每项待改进必须附带：建议方案、固定回顾日期、判断标准

### 阶段 2：观察期数据采集（固定周期，如 30 天）

**4 项最小指标**（不求全，求能持续）：

| # | 指标 | 采集方法 | 频率 |
|---|------|---------|------|
| 1 | **引用深度** | grep 目标文档名 → 按 A/B/C/D 分级统计引用文件 | 每周 |
| 2 | **触发频率** | 搜索系统日志/状态文件中是否出现目标机制的关键词 | 每周 |
| 3 | **信号有效性** | 逐条运行文档中定义的检查命令，对比"健康信号"列 | 每周 |
| 4 | **事实准确性** | 如果目标文档引用了外部系统，检查外部系统是否发生变更 | 变更发生时 |

**采集原则**：
- 每次采集 ≤ 5 分钟。超过说明采集范围太大，需要缩减
- 结果追加到目标文档末尾（或一个简单日志文件），不需要独立报告系统
- 如果第一周就发现"从未被触发"，这本身就是最重要的数据——不必等 30 天

### 阶段 3：数据驱动决策（观察期结束时）

| 数据状态 | 决策 |
|---------|------|
| 引用深度 ≥2 个 D 级 + 触发频率 >0 | **执行拆分**——数据支持拆分有价值 |
| 引用深度停留在 C 级 + 从未被触发 | **不拆**——问题不在粒度，在"为什么没人看这个文档"。先解决可见性问题 |
| 事实准确性下降（≥2 项失真） | **先修正再决定**——不准的情况下拆分会复制错误 |
| 触发频率 >0 且出现异常告警 | **最高优先级**——机制确实在运行且已产生实际影响，值得升级为 Hook 强制执行 |
| 4 项指标全部健康但引用深度为 0 | **降低优先级**——文档自身质量好但没有被引用。考虑是否需要增加交叉引用入口 |

**关键约束**：决策矩阵必须在观察期开始前定义好。不允许在观察期结束时根据同样的数据临时想一个决策理由——这会破坏"数据驱动"的客观性。

## When to Use

- 新建的门禁/规则/检查从"设计完成"到"确认是否需要进一步结构化"之间的过渡期
- 对抗验证发现"应该拆分为更机械的触发"但缺少使用数据时
- 框架/方法论的"从定性到定量"过渡——已经从纸面设计进入工程实现，但还不知道实际表现
- 任何"我们觉得应该改，但不确定改的方向对不对"的结构性变更

## 关键教训

> **从定性到定量的螺旋不能跳步。** 对抗验证 = 定性综合集成。数据采集 = 定量阶段。拆分决策 = 更高层次定性。跳过数据采集直接拆分 = 在纸面上做两轮定性，没有真正的螺旋上升。

> **待改进清单不是拖延清单，但需要"定时器"。** 每条待改进项必须有：固定回顾日期、判断标准、决策矩阵。没有这三样 = 永远不会被处理。

> **最小数据采集 > 完整数据系统。** 每周 5 分钟的 grep 持续 4 周，比一个花 3 天搭建但只用一次的"完美监控面板"有价值 100 倍。
