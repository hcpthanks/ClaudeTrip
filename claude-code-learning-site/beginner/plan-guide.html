① /plan 到底做什么

一句话

/plan 让 Claude 在动手写代码之前，先停下来做一个实现计划——然后等你确认。

核心理念：先想清楚再动手。人做复杂任务需要先规划，AI 也一样。/plan 强制了"规划→确认→实现"这个流程，避免 AI 理解错需求就狂写代码。

/plan 用 vs 不用的区别

不用 /plan用 /plan
需求理解可能理解错，写了半天才发现不对先复述需求给你确认，错了立刻纠正
方案质量边写边想，方案可能不完整全盘考虑后再动手，考虑依赖和风险
浪费写了一半发现方向不对，重来计划阶段就调整方向，几乎零浪费
可控性AI 自己狂奔，你追不上每一步你都看到并确认

② 三种使用方式

方式一：直接输 /plan（最常用）

/plan 我想给用户加一个头像上传功能

Claude 会复述需求、分析风险、列出步骤，然后等你确认。

方式二：带上下文 /plan

/plan 我刚看了 auth.ts，现在想在 login 页面加"记住我"功能

提到具体文件名，Claude 会先去读那个文件再做计划。

方式三：带 PRD 文件 /plan

/plan docs/feature.prd.md

先写一个需求文档（PRD），/plan 读取后生成正式的实现计划写到 .claude/plans/。

③ 什么时候必须用 /plan

✅ 新功能开发

"加一个导出功能"、"新增用户设置页"——涉及多文件修改，必须先规划。

✅ 重构

"把这个大文件拆了"、"把 Redux 换成 Zustand"——影响面大，必须看清全局。

✅ 技术决策

"该用 Redis 还是内存缓存？"——让 /plan 列出利弊，你做决定。

❌ 不需要用 /plan

修复一个明显的小 bug、改一行文字、加一个简单注释——直接说就行。

④ 好用法 vs 烂用法

❌ 烂✅ 好
描述需求 "加个功能" "在设置页加一个导出按钮，点击后下载 CSV，包含所有用户字段"
确认计划 扫一眼就 yes 认真看每一步，确认文件清单和依赖关系
修改计划 不满意也硬着头皮继续 说"modify: 第二步应该先做数据库迁移"
简单任务 改个变量名也用 /plan 简单任务直接做，复杂任务才用 /plan
小心"假确认"：计划出来后不要习惯性点 yes。花 30 秒看一遍——这 30 秒可能省掉后面 30 分钟的回滚。

⑥ 自测练习

Q1：下面哪个场景 不需要 用 /plan？

A. 新增一个导出 CSV 的功能
B. 把用户模块从 JavaScript 重构成 TypeScript
C. 修一个函数名的拼写错误
D. 决定用 WebSocket 还是 SSE 做实时通知

✅ 答案：C — 拼写错误是单行修改，直接改就行。

Q2：AI 给出了计划，你觉得第二步不应该是"写前端组件"而应该是"先加 API 接口"，你应该说什么？

✅ 答案：modify: 第二步应该先加 API 接口，前端组件放到第三步

⑦ 快速掌握清单

  1. 记住触发词：新功能、重构、技术选型 → 必须 /plan
  2. 描述需求时提到具体文件名，AI 会先去读
  3. 计划出来后认真审查，不要习惯性 yes
  4. 修改计划用 modify: 开头
  5. 简单任务（单文件、几行）不用 /plan，别过度使用

⑨ 总结：最常用 & 最易错

🎯 最常用场景

  • 新功能开发 — 涉及多文件修改，先 /plan 再看清全局
  • 重构代码 — 影响面大，用 /plan 列出所有需要改的文件
  • 技术选型 — "Redis vs 内存缓存"，让 /plan 列利弊帮你决策
  • 多步骤任务 — 需要分阶段做的事情，/plan 自动拆步骤
  • 团队协作 — /plan 输出可存档，其他人能看到完整的实现方案

⚠️ 最常犯错误

  • 习惯性 yes — 扫一眼就确认，30秒的审查省掉30分钟回滚
  • 简单任务也用 /plan — 改个拼写、加个注释直接说就行
  • 描述太模糊 — "加个功能" → AI 只能猜，"在XX文件加YY功能" → 准确
  • 不满意也不说 — 直接说 modify: 或 different approach:，别忍着
  • 不提具体文件 — 提到文件名，AI 会先读再计划，准确度高很多
